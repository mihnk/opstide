# M2.5 — Workload and release intelligence

What changed in the cluster today, which Deployments got a new revision, what
exactly changed, did the rollout finish, did the Pods stay up in the minutes
after, and what is still known once Kubernetes has cleaned up the old objects.

Everything below is read-only toward the cluster, runs inside the existing
single-replica collector and SQLite file, and needs no model, Prometheus or Loki.

## What it records

| Concept | What it is | Identity |
|---|---|---|
| Workload | A Deployment OpsTide has seen | the Deployment's UID |
| Release | One revision of a Deployment, as OpsTide saw it | hash of Deployment UID, ReplicaSet UID and revision number |
| Snapshot | An allow-listed copy of that revision's Pod-template settings | stored on the release, fingerprinted |
| Pod record | A compact lifecycle record of a Deployment-owned Pod | the Pod's UID |
| Entry | A meaningful transition, in the existing log, tied to a release | deterministic id per occurrence |

Relationships use `ownerReferences` and UIDs only: Pod → ReplicaSet (by UID) →
Deployment (by UID). A name is never used to decide ownership.

### Decisions worth knowing

1. **A release is a ReplicaSet with a revision number**, not a Deployment status
   change. Scaling, restarts and status updates are not releases. A *rollback*
   makes Kubernetes reuse an old ReplicaSet under a new revision number, so it
   is a new release; the observed entry says "rolled back to the ReplicaSet of
   revision N" only when the ReplicaSet really was an earlier release's. The
   Pod-template fingerprint is not used for that: it leaves out environment
   values and commands, so a `kubectl rollout restart` has the same one. Kubernetes' revision number is not a Git commit, an image tag or
   a CI/CD deployment id, and OpsTide does not pretend it is.
2. **The snapshot comes from the ReplicaSet's template, never from the
   Deployment's current spec.** A ReplicaSet's template is immutable, so it is
   exact for that revision. The Deployment's own settings (replicas, strategy,
   minReadySeconds, progressDeadlineSeconds) are kept only for a release OpsTide
   saw appear, because later they say nothing reliable about it. A comparison
   never "reconstructs" a missing revision; it says it is unavailable.
3. **Observed or adopted.** A ReplicaSet created while OpsTide was watching
   Deployments and ReplicaSets is *observed*. One that already existed is
   *adopted*: its rollout and first minutes were not seen, so it is never
   assessed (verdict: insufficient evidence) and its Pods' earlier history is
   not replayed as entries. Of the older ReplicaSets Kubernetes keeps, only the
   newest is adopted, so a release can be compared with its predecessor.
   A revision that becomes current while OpsTide has watched the Deployment
   without a gap since it last looked is observed even when its ReplicaSet is an
   old one a rollback brought back. A ReplicaSet that is *ahead* of its
   Deployment's revision (the controller creates it first, on a separate watch)
   waits for the Deployment: it is not called replaced, and neither the Pods of
   that ReplicaSet nor their events are written to any release until the
   Deployment has reached that revision (the Pod is retried; a rollback to an old
   ReplicaSet is such a case). Kubernetes timestamps
   have one-second resolution; a ReplicaSet created in the last fraction of a
   second before a watch began can be treated as observed.
4. **Rollout state and health are separate.** The rollout (observed,
   progressing, completed, stalled, failed, superseded, unknown) is what the
   Deployment's own status says. Health (still observing, healthy, degraded,
   insufficient evidence) is what OpsTide saw afterwards. A release can be
   completed and degraded. A completed release stays completed; a later loss of
   availability becomes an *episode* the assessment judges. A release replaced
   before it finished is superseded; one that finished and was then replaced
   stays completed and gets a "superseded" time.
5. **A release's Pods are the Pods of its ReplicaSet that lived during it**, selected
   by ReplicaSet UID and time, not by a stored release id. A rollback reuses a
   ReplicaSet whose Pods never stopped; both the old release and the new one
   show those Pods, each for its own time, and a restart after the rollback is
   written on the new release. A release first seen as its ReplicaSet came up allows
   a minute for Pods created just before it was noticed; a rollback allows none,
   since what its Pods did before the rollback belongs to the earlier release.
   A release replaced at time T stops counting what
   happens after T. A rollback dates the replaced release from when the change was
   seen, never from the old ReplicaSet's creation time.
6. **Health is a pure function of what is stored** (`internal/release`,
   `Assess`): the same input gives the same verdict in the collector and in
   the API, so the release page can judge a release again for 5, 10, 15 or 30
   minutes without writing anything.
   - The window starts when the release was first observed and ends *window*
     after the rollout completed.
   - Counted against a release: OOMKilled; a container restart; a bad waiting
     reason (CrashLoopBackOff, ImagePullBackOff, ErrImagePull,
     CreateContainerConfigError, CreateContainerError, InvalidImageName,
     RunContainerError); a Pod going from Ready to NotReady while not being
     deleted; an eviction; a Pod that ended Failed on its own; availability
     below the target for more than 60 seconds after completion; a stalled or
     failed rollout.
   - Never counted: a new Pod that is Pending, ordinary termination of the
     Pods of a replaced revision, a Pod going NotReady because it is being
     deleted, the restart count of a Pod before OpsTide saw it.
   - Healthy needs a completed rollout, a closed window, nothing against the
     release, and enough evidence. Reaching the desired replica count briefly
     is not enough.
   - Insufficient evidence: adopted; a gap in the Deployment, ReplicaSet or Pod
     watch during the window; replaced before the window ended; no Pod of a
     completed release ever observed. A real problem is still reported as
     degraded even when evidence is also incomplete.
   - While the window is open nothing is final: missing evidence is noted in the
     reasons ("still observing") and decided when the window closes, so a Pod not
     yet read or a short blip never leaves a permanent entry. Only a finding can
     change the verdict before then.
   - **A closed window freezes the verdict.** A release whose window ended, or
     that a newer revision replaced, is not judged again: an eviction a day later,
     retention removing old coverage, or a Deployment update cannot change it.
     Findings carry the time they were seen and only those inside the window count.
     A degraded release is still judged, and swept, while its window is open (more
     can be found); once the window is over, or it was replaced, it is final.
   - A rollout that was stalled or failed stays on the release's record
     ("the rollout was stalled") even when it later completes: it is not clean.
7. **Restarts.** A container restart is recorded once per (Pod UID, container,
   restart count). When the counter jumps by more than one while OpsTide was
   not looking, one entry says how many ("3 restarts since last seen") and has
   no exact time. A Pod first seen while its Pods were not being watched
   (created during a gap) only sets a baseline for restarts, OOMKills and waiting
   reasons: what it did before OpsTide saw it is not counted against anything. The time of a restart is the end of the previous run when
   Kubernetes reports it for a single-step restart, and absent otherwise; it is
   never the observation time. An OOMKill is identified by when the container
   ended, so it is attributed to the right Pod and container and not repeated.
8. **Pending is not failure, CrashLoopBackOff is a waiting reason, and a restart
   is not a release.** A Pod ending during a rollout is information ("replaced
   by a newer revision"), not an error. A Pod that vanished while OpsTide was
   not running is recorded as ended with confidence *unknown*.
9. **No second transport.** Releases and Pod records change the record's version,
   so the existing server-sent `change` event refreshes the Releases page.

## Entry types

Written to the existing log (`events`), each with the release id:

`release.observed`, `release.superseded`, `release.scaled_down`,
`release.paused`, `release.resumed`, `release.stalled`, `release.failed`,
`release.health.degraded|healthy|insufficient`, `release.unavailable`,
`deployment.rollout` (the existing "rollout completed" entry, now tied to its
release), `pod.created`, `pod.ready`, `pod.notready`, `pod.restarted`,
`pod.oomkilled`, `pod.waiting`, `pod.evicted`, `pod.terminated`.

The Log has three new groups: **releases**, **workload health** and **pod
lifecycle**. Releases and health are on by default; pod lifecycle (the
routine) is off. On a release's page Pod entries are folded under their Pod and
open on their own when something went wrong.

## Storage (migration 3)

- `events.release_id` (+ partial index), `workloads`, `releases`,
  `release_pods`. No complete Kubernetes object is stored. The snapshot is an
  allow-list: container names, images, image IDs (digests) reported by the
  first Pod, CPU and memory requests and limits, readiness, liveness and
  startup probes, environment variable **names**, ConfigMap and Secret
  **names**, service account name, a few identifying labels, and the
  Deployment-level settings above.
- Never stored: Secret values, literal environment values, command lines (an
  exec probe keeps a 10-character hash of its command so a change shows), the
  query string of an HTTP probe path, tokens, annotations, other labels, a
  whole spec. A test fails if a literal value leaks into a snapshot.
- The informer's cache trims a ReplicaSet's template to what the snapshot takes
  (environment values, commands, arguments, mounts and ports are dropped on
  arrival); a probe's exec command is still read, to be hashed.
- Retention: events follow the existing retention. A release (with its Pods) is
  removed after the retention period unless it is the newest of its workload;
  finished Pod records go with retention. A Pod record stays as long as its
  ReplicaSet belongs to a kept release, whichever release it was first recorded under.
- A Deployment deleted while OpsTide was not running is noticed at the next
  start: it is marked deleted, dated by the time it was noticed, and its releases
  settle.
- Upgrading adds the tables (one-way, as migration 2 was).

## API (all under `/api/v1`, schema 1, existing token authentication)

| Endpoint | What |
|---|---|
| `GET /releases?namespace=&workload=&state=&health=&within=7d&from=&to=&history=&limit=&cursor=` | The release list, newest first, with recent significant entries and coverage warnings |
| `GET /releases/{id}?window=5\|10\|15\|30` | One release with its assessment (judged again for `window` when given) |
| `GET /releases/{id}/events?limit=&cursor=` | The release's timeline |
| `GET /releases/{id}/pods` | Its ReplicaSet and Pods with readiness history, restarts and terminations |
| `GET /releases/{id}/changes` | Field-level comparison with the preceding observed revision, or why none is possible |
| `GET /events?release=<id>&show=releases,health,pods` | The log, filtered by release and the new groups |

Limits: pages of at most 200 releases / 500 entries, 500 Pods per release, ranges
up to 400 days, known state and health names only.

## UI

A **Releases** page (list with filters, coverage warning, adopted marker) and a
release page with **Overview, Timeline, Pods, Changes and Investigation
context**; new Log groups; and a **Release observation** section on System. The
Investigation context tab is a deterministic summary of what OpsTide holds; the
Investigate button stays disabled. The design board is in the Claude Design
canvas for OpsTide.

## Cost and scale

- Two watches are new: ReplicaSets, and Pods with a `pod-template-hash` label
  (the label the Deployment controller puts on its Pods), so the API server drops
  every other Pod before OpsTide sees it. The existing Job-Pod watch is unchanged.
- The Pod cache keeps only metadata identity, owner references, node name and
  status. MEASURED on a synthetic but realistic Pod (two containers, 25
  environment variables, managed fields): 10.6 KB as received, 2.6 KB kept, so
  5,000 Pods are about 13 MB instead of 53 MB. Real Pods vary.
- Handlers only queue keys. A Pod change reads the cache and does a few indexed
  reads; nothing is reprocessed cluster-wide on an update, and nothing is
  written unless the Pod's record changed. There is no per-Pod timer. The one
  timer is a sweep every 30 seconds over releases still being observed.
- Memory limit in the chart stays 512 Mi; a cluster with tens of thousands of
  Deployment Pods should raise it and narrow `namespaces`.

## Limitations (stated, not hidden)

- Only Deployments, not StatefulSets, DaemonSets or Argo Rollouts.
- Pod entries are written from Pod status as it changes; a container that
  restarts and recovers between two status updates is seen as one restart with
  a delta, with no exact time.
- A Pod deleted and gone before the worker reads it is recorded from its last
  state in the cache's delete notification, which has no later status.
- Environment values, commands and other template fields outside the allow-list
  are not captured, so a change to only those shows as "no captured
  differences" (the ReplicaSet differs; nothing allow-listed did).
- Image IDs are known only once a Pod reports them.
- `kubectl rollout restart` makes a new ReplicaSet with an identical template:
  it is a release whose changes say "no captured differences".
- A scale-up inside the window (an autoscaler going from 2 to 10) leaves fewer
  replicas available than wanted until the new Pods are Ready; if that lasts more
  than a minute it counts as an availability shortfall, which can read as a
  degradation the rollout did not cause.
- An exec probe's command is kept as a 10-character hash so a change shows. It is
  not reversible for a long command, but a short or guessable one can be guessed
  from the hash; keep credentials out of probe commands (they should not be there
  anyway).
- A release that is still being observed is judged again each time its page is
  opened (the list shows the verdict the collector stored; they differ by at most
  30 seconds). Once a verdict is final the page shows it exactly as stored, and
  works out the findings and evidence again only to display them. A window chosen
  with `?window=` is a question asked now and is answered now (`stored: false`).
- Any Pod readiness change anywhere makes the record's version change, so open
  pages refetch (at most once per refresh tick).
- The observation window is a server setting (`releases.observationMinutes`);
  the release page can judge by another length but does not change what is stored.
- Not covered here: Pod entries do not replace container logs, which are not kept.
- Verified against a real kube-apiserver (envtest) with hand-made objects, not
  against a live cluster with controllers and a kubelet; no kind run was possible.
