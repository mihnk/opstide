# M2.6: Kubernetes evidence and event correlation

OpsTide records evidence. Agents interpret evidence.

Nothing in this milestone produces a hypothesis, a probable cause, a causal
sentence, a summary written by a model or a recommendation. Three kinds of thing
are shown, and kept apart:

1. **Observed**: what Kubernetes reported (an Event's reason, type and message;
   an autoscaler's desired replicas and conditions).
2. **Derived**: a result of a documented rule on observed values, with the rule
   named (for example `scaling.convergence`).
3. **Unknown**: what the source did not give. A missing time or count is `null`;
   a resource OpsTide never saw is `UNRESOLVED`.

A Kubernetes `reason` or `message` is Kubernetes' observation, not a proven
cause, and is never turned into a stronger claim.

## What is collected

| Source | How | Kept |
|---|---|---|
| Events | `events.k8s.io/v1`, list and watch | An allow-listed record per Event UID |
| HorizontalPodAutoscalers | `autoscaling/v2`, list and watch | Observed state, and entries for changes |
| Deployment replica target | the Deployments already watched | An entry when `spec.replicas` changes between two observations |

Both Event watches and the autoscaler watch are **optional**: they start with the
collector but readiness does not wait for them, and a cluster that forbids
reading Events still has runs and releases recorded. System shows what cannot be
read.

### One API, never both

An Event is one object with one UID served by two APIs. OpsTide reads it through
`events.k8s.io/v1`, and through `core/v1` only if discovery shows the cluster does
not serve the first (a failure to ask is not taken to mean it does not). The two
are never read together; the Event's UID is its identity either way. The record
says which API it came through, and where the API's own semantics differ it
says which field a value came from:

* first time: `deprecatedFirstTimestamp`/`firstTimestamp`, else `eventTime`;
* last time: `series.lastObservedTime`, else `deprecatedLastTimestamp`/`lastTimestamp`, else `eventTime`;
* count: `series.count` (basis `series`), else `deprecatedCount` / `count`
  (basis `deprecatedCount` / `count`); none given means `null`, not 1.

### Which Events are kept

Events about Pods, ReplicaSets, Deployments, Jobs, CronJobs and
HorizontalPodAutoscalers. Events about anything else (Nodes, Services, volumes)
are not read into the record.

### Updates, not duplicates

The record is keyed by the Event's UID. A count that grows, a changed message or
a later last-time changes the one row; nothing is written when nothing changed.
A Warning Event writes one Log entry when first recorded
(`evidence.event`); a later increase writes one explicit
`evidence.count_changed` entry (from and to), at most once per Event per five
minutes. Normal Events are kept as evidence and do not enter the Log.

### Adopted Events

An Event already present when OpsTide began watching its scope is `adopted`: the
record keeps the times Kubernetes gave it, says when OpsTide first saw it, and is
never dated at startup. Whether an Event was seen while watching uses the same
coverage intervals as releases. Earlier occurrences are not reconstructed.

### When Kubernetes drops an Event

The evidence stays for the retention period (and the same entry cap as the Log).
`sourceDeletedAt` says when OpsTide saw Kubernetes drop it. An Event that vanished
while OpsTide was not running is marked at the next start, dated by the time it
was noticed (not by when it happened).

### Bounds and privacy

* Message: first 1 KiB, cut on a character boundary; `messageTruncated` says so.
  Other fields are cut at 253 bytes. The in-memory cache holds the trimmed
  Event, and an Event about an unfollowed kind only its identity.
* Message bodies are never logged by OpsTide, and never sent anywhere.
* The UI shows messages as text (React escapes them); long ones fold.
* Only the API's existing authentication and read-only boundary apply. The chart
  adds `list` and `watch` on `events.k8s.io/events`, `autoscaling/horizontalpodautoscalers`
  and, for the `core/v1` fallback, `events`.

## Relationships

Links are made only from the UID an Event states and from ownerReferences, first
from what OpsTide recorded (it survives garbage collection of Pods, ReplicaSets
and Jobs) and then from the informer caches. Never from a name, never from time.

| Classification | Meaning |
|---|---|
| `DIRECT` | the Event names the resource by UID |
| `OWNERSHIP` | the resource is linked to another through ownerReferences (Pod to ReplicaSet to Deployment, Pod to Job to CronJob) |
| `SAME_RESOURCE_CONTEXT` | both concern the same resource or workload; nothing is asserted between them. An autoscaler's `scaleTargetRef` names its Deployment by name, so that link is recorded as this, with the way it was made |
| `UNRESOLVED` | not enough evidence to link them. An Event naming no UID, or a resource OpsTide never saw, is kept like this |

They classify the link. They are not confidence scores and not claims about cause.

A Pod's Events are linked again when the Pod is first recorded; a ReplicaSet's
and Deployment's when the release or workload is. An Event that stays unlinked
says so.

### Evidence of a release

`GET /api/v1/releases/{id}/evidence` returns, for each record, how it relates to
the **release** (separate from how it relates to the resource it names):

* `DIRECT`: it names this release's ReplicaSet;
* `OWNERSHIP`: it names a Pod that ReplicaSet owns;
* `SAME_RESOURCE_CONTEXT`: it names the Deployment, or an autoscaler targeting
  it, recorded while this release was current.

An Event belongs to the window when it overlaps it: it began before the window
ended and was last seen after it began, so a Warning that began under a release
and kept repeating after a newer revision took over is still that release's.
The window is from the ReplicaSet's creation (observation, for a rollback, whose
ReplicaSet is older) until a newer revision took over. Events about Pods of an
older ReplicaSet are not this release's. Time is used to bound the window and
never to link a record.

## Scaling

* `hpa.desired_replicas_changed`, `hpa.condition_changed` (a condition's status
  or reason changed), `workload.replica_target_changed`: each is a change between
  two observations, stated as reported. The first status an autoscaler reports
  (it is created with none) is a baseline, not a change.
* None says why. A replica-target change is not assumed to be an autoscaler's;
  the autoscalers that target the Deployment are listed beside it as context.
* A replica-target change is never a release: releases come only from ReplicaSets
  with a revision.

### Release assessment: rule set 2

The M2.5 rules counted any availability shortfall longer than 60 seconds after
completion. After a scale-up that counts the Deployment catching up with its new
target.

Rule set **2** (new releases) records, when a shortfall begins with a raised
replica target while at least the earlier target was available, the target
change and the lowest available count seen since (sampled each time the
Deployment's status changed):

* `scaling.convergence`: the lowest available count stayed at or above the
  earlier target. Not counted; reported as context with its inputs.
* `scaling.below_earlier_target`: available fell below the earlier target. Counted,
  with the scaling stated.
* `scaling.replica_lost`: available fell from one count to a lower one while the
  target was still at least the higher count, even if it stayed above the earlier
  target: a replica that was serving was lost, which is not catching up. Counted.

If the target is raised again during the episode it is recorded (`to` is the
highest target seen). A scale-up that had not reached its target when the window
closed is context, not a finding, and the healthy verdict then says "no loss of
availability below the earlier target" rather than "no lasting loss of
availability", and the context line says the target had not been reached.

Everything else still counts: a restart, OOMKill, waiting reason, NotReady
transition, eviction, a stalled rollout, and a shortfall that did not begin with
a raised target. Scaling never clears a directly observed failure.

Each release keeps the rule set it was created under
(`assessment_version`, shown on the release). Releases recorded before this
milestone keep rule set 1, and a verdict already reached is never read under
other rules. When the verdict is shown, the rule set is shown with it.

## The facts-only summary

Built in Go from structured records by documented rules (`internal/evidence`),
no model. Each line names its rule and the records it came from. Lines:
`release.observed` / `release.adopted`, `release.pods_observed`,
`rollout.reported`, `event.reported` (Warning Events, grouped by reason and
resource), `event.more`, `scaling.hpa_desired`, `scaling.replica_target`, and
the context notes. Normal Events are listed in the records, not the summary. It
always ends with "Root cause: Not established by OpsTide.", and says when the
records were cut off at their limit (the records themselves are always there).

## Storage (migration 4)

`evidence` (one row per Event UID, indexed by UID, regarding UID, ReplicaSet,
Deployment, Job run, autoscaler, namespace, reason and time), `hpas`, the
`events.reason` and `events.workload_id` columns (and partial indexes),
`workloads.spec_replicas`, `releases.assessment_version`. One way, like earlier
migrations. Retention prunes evidence by age and by the Log's entry cap.

## Resource use

Two more watches (Events, autoscalers), neither blocking readiness; no new timers.
A harmless refresh writes nothing. A growing count is one UPDATE; the Log gains at
most one entry per Event per five minutes. Metrics are low-cardinality
(`opstide_evidence_events_total{origin}`, `opstide_evidence_updates_total`,
`opstide_scaling_entries_total{type}`, `opstide_evidence_records`).

## Not supported

* Events about kinds other than those listed; Events with no UID are kept but never linked.
* Reconstructing occurrences before the first one OpsTide saw, or any count Kubernetes did not give.
* Linking by name or by time; a Pod OpsTide never recorded (a standalone Pod) is unresolved.
* The `deletedAt` of an Event that expired while OpsTide was down.
* Replica availability is sampled whenever the Deployment's status changes: `MinAvailable` and the lost-replica check use those samples, not a continuous record.
* HPA condition entries are written for every change of a condition's status or reason; a reason that flips often writes often (bounded by what the HPA reports).
* Events of Pods of Jobs that arrive before the Pod is recorded are not re-linked later (Deployment Pods are).
* An evidence row pruned by the entry cap while its Event still exists is recorded again at its next update, with a new first-seen time.
* Not measured: the cost of a cluster-wide Events relist on a very large cluster (each Event is one write through the shared worker queue).
* StatefulSets, DaemonSets, other autoscalers (KEDA and the like), custom metrics beyond what the HPA's own status reports.
* Anything interpretive: causes, hypotheses, recommendations.
