# M2.7: StatefulSets, DaemonSets, Nodes and complete Job evidence

OpsTide records evidence. Agents interpret evidence.

Everything here follows the rules of [M2.6](M2.6-EVIDENCE.md): what Kubernetes reported (observed),
what a documented rule calculated from it (derived, with the rule named), and what is not known. Nothing
here says why something happened, whether a workload is healthy, or what to do. A Kubernetes `reason`
or `message` is Kubernetes' observation, shown as such.

## What is observed

| Kind | Watch | Kept |
|---|---|---|
| StatefulSet | `apps/v1` StatefulSets | identity, strategy, partition, Pod management, status counts, revisions, conditions |
| DaemonSet | `apps/v1` DaemonSets | identity, strategy, `maxUnavailable`/`maxSurge`, status counts, revisions, conditions |
| ControllerRevision | `apps/v1` ControllerRevisions | the allow-listed snapshot of the Pod template (see Privacy) |
| their Pods | Pods with the `controller-revision-hash` label, filtered by ownerReference | lifecycle (as Deployment Pods), revision, node, ordinal |
| Node | `core/v1` Nodes, **only when `nodes.observe` is on** | identity, `spec.unschedulable`, five conditions |

All of these watches are optional, like Events and HPAs: they start with the collector but readiness does
not wait for them, and a cluster that forbids reading them still has runs, Deployments and releases
recorded. System says what cannot be read. Each group is reconciled (objects removed while OpsTide was down)
only once its own watches have listed, so a watch that failed is never taken to mean objects are gone.

### One workload model

`workloads` holds Deployments, StatefulSets and DaemonSets, each keyed by its **own UID** (`kind` says which).
`workload_state` is the current observed state of all three, so one list can show them. Deployments keep their
revisions in `releases` (ReplicaSets); StatefulSets and DaemonSets keep theirs in `workload_revisions`
(ControllerRevisions). Revision numbers are only meaningful inside their own workload and are never compared
across workloads. CronJobs and Jobs stay scheduled operations. A Deployment's release model is unchanged.

## StatefulSet rollout, by a documented rule

`internal/workload.ClassifyStatefulSet`; the note stored with the state quotes the values it used.

| State | When |
|---|---|
| `unknown` | Kubernetes has not reported status for the current generation (`observedGeneration` < `generation`) or no update revision yet |
| `completed` | `currentRevision` equals `updateRevision` |
| `updating` | the revisions differ and the update has not reached its boundary |
| `partitioned` | RollingUpdate with `partition` > 0 and `updatedReplicas` ≥ `replicas − partition`: the rollout stopped where it was told to. **Not a failure.** |
| `awaiting_pod_deletion` | strategy OnDelete, the revisions differ and not every Pod is on the update revision: a changed template replaces no Pod until it is deleted. **Never reported as completed by the template change alone.** |

Under OnDelete the controller does not advance `currentRevision`, so the revisions stay different; when every Pod has been replaced (`updatedReplicas` covers `replicas`) the state is `completed`, with a note saying so.

There is no "failed" or "stalled" state: a StatefulSet's status has no such condition, and OpsTide does not
invent one. A condition a controller does report is recorded as reported (`…condition_changed`).

## DaemonSet rollout

A DaemonSet's status has no revision. Its **template revision** is its newest ControllerRevision (the highest
`revision` number), and while the ControllerRevision watch has not listed yet it is *unknown* and stays what it was: learning
the first revision, or an unfilled cache, is never a template change; `completed` means `updatedNumberScheduled` covers `desiredNumberScheduled`; OnDelete with
fewer updated is `awaiting_pod_deletion`; otherwise `updating`. Availability is reported beside it as counts and
is not part of the state. Desired, current, updated, ready, available and misscheduled counts changing is a count
change: **a changing number of nodes is never a new release or application revision.**

## Entries (Log)

`statefulset.observed`, `.revision_changed`, `.current_revision_changed`, `.partition_changed`,
`.strategy_changed`, `.update_started`, `.update_partitioned`, `.update_awaiting_pod_deletion`,
`.update_completed`, `.condition_changed`, `.deleted`, and the same for `daemonset.` (without the StatefulSet-only
ones); `…counts_changed` lists what Kubernetes reported changed (`ready 3 to 2, available 3 to 2`). The first sight
of a workload is a baseline: one "first observed" entry, and no rollout entry for an update it joined in the middle.
Counts are routine, so they are a Log group of their own, off by default, and left out of the unfiltered API.
Pod entries for these Pods are the same `pod.*` entries as for Deployments.

## Pods, ordinals and nodes

A Pod belongs to the StatefulSet or DaemonSet its **ownerReference** names (by UID). Its revision is its own
`controller-revision-hash` label (a StatefulSet Pod carries the revision's name, a DaemonSet Pod its hash). A
StatefulSet Pod's ordinal is the `apps.kubernetes.io/pod-index` label when present, else the name read the
way the controller builds it (`<name>-<index>`, exactly); a name that does not have that shape has no ordinal.
The Node is `spec.nodeName` as the Pod reported it: **placement context, not ownership**, kept with the Pod's
record after the Pod is gone. A Pod OpsTide did not observe is not listed and no placement is invented.

DaemonSet Pods page: each Pod's node and whether it runs the update revision. When Node observation is on, Nodes
with no live Pod of the DaemonSet are listed **as that fact only**: whether a Node is eligible (selector, taints,
tolerations, affinity) is not read, so no explanation is given and a missing Pod is not called an application error.
With Node observation off, nothing is said about nodes without a Pod.

## Nodes (cluster-scoped, off by default)

Needs `list`/`watch` on `nodes` cluster-wide; the chart adds a small ClusterRole only when `nodes.observe=true`
(also for installs limited to some namespaces) and never otherwise. `OPSTIDE_OBSERVE_NODES=true` /
`--observe-nodes`. System shows whether it is on, how many Nodes are recorded, and any watch problem.

Recorded: the Node's UID and name, `spec.unschedulable`, and **Ready, MemoryPressure, DiskPressure, PIDPressure,
NetworkUnavailable** with each condition's status, reason, message, the source's `lastTransitionTime` and when
OpsTide first saw the status. Not read: capacity, addresses, labels, taints, images.

* `node.condition_changed` (a status changed), `node.unschedulable_changed`, `node.observed` (a Node created while
  OpsTide watched), `node.deleted`. A Node already present at start is **adopted** and writes no entry, so a cluster's
  Nodes are not a log; the first conditions a Node reports (it is created with none) are a baseline.
* `spec.unschedulable` changing proves only that the field changed. Who or what changed it is not said (no "cordon" and no
  "operator"), and the field alone does not say whether Pods can be scheduled (taints and conditions are separate). A `Ready` of Unknown is shown as Kubernetes' words (`NodeStatusUnknown`),
  never as a failed machine.
* Events about a Node: kubelet reports the Node's **name** as the Event's UID; the Node controller reports the real
  UID. A UID OpsTide recorded links directly. Otherwise the exact name of the one live Node of that name is used, because
  Nodes are cluster-scoped and Kubernetes refers to them by name (as `spec.nodeName` does); the link says so
  (`regarding names the Node (exact name…)`) and is never a similarity match.
* The Node page shows the Pods observed on a Node of that name while that Node existed (a recreated Node of the
  same name is another Node), its recorded transitions, and the Events that name it. It is not an inventory.

## Job and CronJob evidence, completed

An Event about a Job's Pod can arrive before the Pod is known. When the Job's Pod is recorded, evidence that named it
and has no run is linked to the run and its CronJob, from the Pod's **ownerReference** only; the Event's identity
and times are untouched, and no second record is made. Evidence that names a Job by UID gets its CronJob when the
run's CronJob is known. The ownership (`pod_owners`: Pod UID → Job UID → CronJob UID, with the node) is kept after the
Pod and Job are garbage-collected, so an Event that arrives later still links. Nothing is linked by name. An Event
with no authoritative relationship stays `UNRESOLVED`. The run detail shows its Events as Kubernetes reported them
(reason, message, times, count, source, the relationship) with the limits of what can be shown.

## Privacy

A ControllerRevision's data holds the whole Pod template, literal environment values and commands included. It is
reduced to the allow-listed snapshot (`internal/release.FromTemplate`) **in the informer's transform**, the moment
it arrives: container names and images, resources, probes, the **names** (never values) of environment variables,
ConfigMaps and Secrets, the service account. The values are never held in memory or stored, and the database is
checked for them. A revision whose template cannot be read says so ("Comparison unavailable: …") and is not guessed.

## API

| Route | |
|---|---|
| `GET /api/v1/workloads?kind=&namespace=&q=&status=live\|deleted&within=&limit=&cursor=` | all three kinds, by last change; no score |
| `GET /api/v1/workloads/{id}` | identity, state, sections, the Deployment's current release |
| `GET /api/v1/workloads/{id}/history` | entries about it (routine Pod entries left out unless `pods=all`) |
| `GET /api/v1/workloads/{id}/revisions` | revisions with the comparison to the one before, or why it is unavailable |
| `GET /api/v1/workloads/{id}/pods` | Pods with ordinal, revision role, node; DaemonSet Nodes without a Pod |
| `GET /api/v1/workloads/{id}/evidence` | Events linked to it and the conditions Kubernetes reports |
| `GET /api/v1/nodes`, `/nodes/{id}`, `/nodes/{id}/history` | Node context |
| `GET /api/v1/runs/{id}/evidence` | the Events linked to a run |

`/events` gains the groups `statefulsets`, `daemonsets`, `nodes`, `counts`; the existing `/releases`, `/operations`,
`/runs`, `/evidence` and `/workloads/{id}/scaling` are unchanged. Every list is bounded and paged.

## Storage (migration 5)

`workloads.kind/origin`, `workload_state`, `workload_revisions`, `nodes`, `pod_owners`, and columns on
`release_pods` (`kind`, `revision`, `node`, `ordinal`) and `evidence` (`node_id`). Deployment release and rollout
entries now name their workload (existing ones are filled in by the migration). One way, like earlier
migrations. Retention: revisions are kept past Kubernetes garbage collection but not past retention (the newest
revision of a workload that still exists stays; those of a long-deleted workload go with it); `pod_owners` and removed
Nodes follow retention; StatefulSet/DaemonSet Pod records are removed with their workload.

## Resource use

Four more namespaced watches (StatefulSets, DaemonSets, ControllerRevisions, and Pods carrying
`controller-revision-hash`, which the API server filters), plus Nodes if turned on. Caches are trimmed:
workloads keep their spec's scalar fields and status; ControllerRevisions only the snapshot; Pods only what the
lifecycle record reads and two labels. A change writes nothing when the observed state's hash is unchanged. No new
timers or goroutines per object. Metrics are low-cardinality (`opstide_workloads{kind}`, `opstide_nodes`).
Broad Pod observation: the Pod watch for these kinds holds every StatefulSet and DaemonSet Pod of the scopes
watched (trimmed to about the size of a Deployment Pod's); on a cluster with thousands of such Pods that is the
dominant cost, and `namespaces` narrows it.

Ownership is checked by Kind **and** API group (`apps/`): a third-party Kind with the same name (for example OpenKruise) is
not treated as a StatefulSet or DaemonSet. A rollback gives an existing ControllerRevision a higher `revision` number;
the stored number follows it, so a revision sorts and compares as the newest it is.

## Known limits

* Reconciliation of StatefulSets, DaemonSets and their Pods runs once all three watches have listed: if one of them is forbidden, the
  others are not reconciled (nothing is marked deleted wrongly, the safe direction).
* The workload list is ordered by the last change, which moves: a workload that changes between two page loads can be skipped by the cursor.
* The first start after migration 5 sets every Deployment's last change to that moment, so a "changed in" filter matches them for a while.
* `pod.*` entries written before migration 5 are not in a Deployment's history (they stay in its releases).
* A ControllerRevision pruned by retention while Kubernetes still holds it is recorded again at its next sync, with a new first-seen time.
* `pod_owners` is pruned with retention: a Job Pod that outlives it loses late binding.
* Turning Node observation off leaves recorded Nodes as they were (shown live) and exact-name Event links keep using them; it is not a reset.

## Not supported

* A failure or stall state for StatefulSets and DaemonSets (Kubernetes reports none).
* Node eligibility for a DaemonSet (selectors, taints, tolerations, affinity), capacity, labels, taints, images, metrics.
* Linking by name, except the exact-name reference of a cluster-scoped Node, stated as such.
* Pods and Nodes OpsTide did not observe; history from before OpsTide watched, except ControllerRevisions Kubernetes still held.
* A DaemonSet's "current revision" (its status has none); the newest ControllerRevision is shown instead.
* StatefulSet `ordinals.start` and persistent-volume claim retention.
* Job Pods are not placed on Nodes in the Node page (their Node is kept in `pod_owners` only).
