# M2.8: Operational Evidence Explorer

OpsTide records evidence. Agents interpret evidence. The Explorer shows what was recorded, on one timeline, with where
each fact comes from and where OpsTide was not looking. It does not say what caused anything: there is no root-cause
text, no score, no remediation advice and no model. A relationship between two records says how they are connected,
never that one caused the other.

## One read model, no second table

The Log (`events`) and the Kubernetes Event record (`evidence`) stay as they are. The Explorer reads both, each on its
own index and bounded by the time range and the page size, and merges the few rows that come back. A Kubernetes
Warning Event is both an `evidence` row and an `evidence.*` Log entry; the Explorer shows the row only, so each fact
appears once. Nothing is held in memory beyond one page per source.

Ordering. Every record has one *record time* that never changes once written: the time the source gives (a Log entry's
occurrence time; a Kubernetes Event's first occurrence), otherwise the time OpsTide first observed it. It is never
invented; `observedAt` is always kept beside it. Ties break on the record id (`e.<seq>` for a Log entry, `k.<id>` for a
Kubernetes Event). The cursor is `<record time ms>.<record id>`, so paging neither skips nor repeats a record, also when
a Kubernetes Event is updated later (a repeat count does not move it).

Routine records are Pod created/ready/terminated and Normal Kubernetes Events. They are hidden by default and counted
(`suppressedRoutine`); `routine=1` shows them. Nothing else is hidden. Text search covers names, reasons and
summaries, never Event messages.

## Provenance

`OBSERVED` (Kubernetes reported it, recorded as reported), `DERIVED` (a documented rule applied to observations; the
drilldown shows the rule id, the rule-set version where one is stored, the inputs and the records it was computed from)
and `UNKNOWN` (OpsTide records that it does not know). Sources: `kubernetes.api`, `opstide.rule`, `opstide.coverage`,
`kubernetes.events.k8s.io/v1`, `kubernetes.core/v1`.

## Coverage, and the five empty states

`/api/v1/explorer/context` gives, for a range: each watch with its watched spans and gaps, whether it is unavailable
or switched off (Node observation is off by default), when OpsTide first observed the cluster, and the retention
boundary. An empty timeline says which of five different things it is, and they are never merged: *no matches* (watched
throughout, nothing recorded matches), *source unavailable* (the watch is off or unreadable), *outside retained history*,
*before first observation*, *collection gap* (not watched for part of the range, so an empty result is not proof).

## State at a time

`/api/v1/explorer/state?uid=&at=` answers what OpsTide knew of one resource at a past time: `OBSERVED_AT` (a change was
recorded at exactly that time), `TRANSITION` (the latest recorded change before it), `LATEST_RECORD` (only a Kubernetes
Event is recorded) or `UNKNOWN` ("Not enough recorded evidence to determine this state."). It never fills in a state it
did not see. Live state is only ever offered as a link labelled as the current state.

## Export

`opstide.explorer.export` version `1.0`, a download made only when asked for. Records are oldest first, ties by id.
Each keeps its id, type, source, resource identity, source UID, record/occurred/observed times, provenance, source
fields, rule reference and relationship classifications (`DIRECT`, `OWNERSHIP`, `SAME_RESOURCE_CONTEXT`,
`UNRESOLVED`). The document carries its scope, filters, generation time, coverage with gaps and unavailable sources,
retention limits and counts. A filtered export stops at 5,000 records and says so (`truncation.nextCursor` continues
it); a selected export takes at most 1,000 ids and lists the ones no longer held. Kubernetes Event messages, and quoted
condition messages in Log entries, are left out unless `messages=1` / `includeMessages` is sent (the UI warns). Payloads
are never logged and nothing is sent anywhere.

## Investigation Workspace

A list of record ids kept in the browser tab's `sessionStorage`: no server write, no accounts, no saved
investigations. Records are added with the `+` beside them in the Explorer, the Log, release, workload, Node and run
views. The page counts what is selected by kind, provenance, resource kind, namespace and source, names where watching
was not whole over the selected period, sorts chronologically, and exports the selection. It writes no narrative.

A record about a Pod leads on to the revision it belongs to: the release of its ReplicaSet for a Deployment's Pod, the
ControllerRevision its `controller-revision-hash` label names for a StatefulSet's or DaemonSet's (marked not recorded
when OpsTide holds no such revision).

## Correctness items that came with it

* A workload's page shows revision progress (updated replicas) apart from observed availability (ready, available).
* With Node observation off, Nodes are not shown as live: `status: not_observed`, `lastObservedAt`; System counts 0 live;
  Events are not linked to a Node by name.
* A Node recreated under the same name is another Node. A Kubernetes Event that names a Node by name is linked only to
  the Node of that name that existed when it happened (1 s clock allowance), otherwise it stays unresolved.
* A workload's page says *first recorded*, *last observed* and *last meaningful change*. Something already there when
  OpsTide began (or when migration 6 ran) gets a `baseline` last change (its newest release, ControllerRevision or
  creation time), not "now".

## Storage

Migration 6 adds the Explorer's indexes (`events_resource`, `events_run`), the `change_basis` column, and the Deployment baseline above. Migration 7 stores a Kubernetes Event's record time (`record_key`) once, when it is first recorded, and indexes it: Kubernetes may add a timestamp to an Event later, and the stored time keeps the Event from moving on the timeline. Measured on 300,000 Log
entries and 100,000 Kubernetes Events over 30 days: a 100-record page 40 ms, by resource UID 1 ms, by workload 8 ms,
text search 260 ms, filter counts over 30 days 0.8 s (cached per record version).

## Known limits

Missed and unconfirmed scheduled runs are computed on demand from schedules and are not records, so the Explorer
does not list them. The state-at-time view reads recorded transitions only, so it can say less than a live cluster could.
Grouping by resource works within the records loaded on the page.
Evidence is pruned by its last occurrence but placed by its first, so an Event that keeps recurring can sit in a stretch
older than the retention boundary.
